# t3 mini

A small, local coding-agent workspace built with **TanStack Start**, React, and TypeScript. Threads live in the left sidebar; the conversation lives on the right. Choose **Codex** or **Claude Code** for each thread.

## Run

Requires Node.js **22.12+** (or a newer supported Node release) and [Bun](https://bun.sh) as the package manager. The dev server runs on Node; Bun installs dependencies, runs the scripts, and is the runtime inside the installed `t3mini` binary.

```sh
bun install
bun run dev
```

### Install (`t3mini`, the production copy)

On any Mac or Linux machine (a VPS, another computer), install the latest release with one line, no repo or Node needed:

```sh
curl -fsSL https://raw.githubusercontent.com/edwinencomienda/t3mini/main/install.sh | sh
t3mini start
```

It picks the binary for the machine (macOS or Linux, arm64 or x64), checks it against the release's checksums, and installs it to `~/.local/bin` (`| sh -s -- v0.1.1` for a specific version). On such a machine, `t3mini update` downloads the newest release. Claude Code and/or Codex still need to be installed and signed in there.

From the repo (your own build, and the two-copy setup below):

t3 mini can run as two separate copies, so you can work in a stable one (including on t3 mini itself) while changing the other:

|                    | Production: `t3mini`                      | Dev: `bun run dev`                      |
| ------------------ | ----------------------------------------- | --------------------------------------- |
| Address            | **http://127.0.0.1:4011**                 | **http://127.0.0.1:4016**               |
| Data               | `~/.t3-mini/data`                         | `.data` in the repo                     |
| Phone access ports | 4311 / Tailscale 8443                     | 4316 / Tailscale 8444                   |
| Code               | A single compiled binary (Bun), installed | The repo, with hot reload (Node + Vite) |

```sh
bun run install-cli   # build the binary and install it to ~/.local/bin/t3mini
t3mini start          # run it in the background → http://127.0.0.1:4011
t3mini status | stop | restart | logs | open
t3mini update         # rebuild and reinstall from this repo (restarts it unless a thread is running)
t3mini import .data   # once, to bring your dev threads and settings over (into an empty data folder)
```

`t3mini` is one file (about 85 MB) with Bun and the built app inside, so it needs nothing else installed except the agents (`claude`, `codex`). It keeps its pid, log, and settings in `~/.t3-mini` (put `DEEPGRAM_API_KEY=…` and other variables in `~/.t3-mini/.env`; a `.env` in the folder you start it from is ignored). Each copy blocks only its own ports from the agents' browser, so an agent in production can open the dev copy to check a change. `bun run compile --all` also builds Linux (x64, arm64) and Intel Mac binaries into `dist/bin`.

**Updating production** (after you change t3 mini or pull new commits):

1. Try the change in dev first: `bun run dev` → http://127.0.0.1:4016.
2. Run `t3mini update` (from anywhere), or `bun run install-cli` in the repo. Both rebuild the binary from the repo **as it is now, including uncommitted changes**, install it over `~/.local/bin/t3mini`, and restart production if it was running.
3. If a thread is still working in production, the restart is skipped (it would stop that turn): the update lists the running threads, the new binary is already installed, and `t3mini restart` switches to it once they finish. `t3mini update --force` restarts anyway.
   Production's sidebar also shows **t3 mini update installed** with a **Restart** button (Mac only). While agents are working it offers **When done** (production restarts itself as soon as every thread is idle) or **Restart now** (asks first, since it stops their turns). The page reloads itself on the new version.
4. `t3mini status` shows the commit it was built from (`Source: … @ <commit>`).

Updating never touches data: production keeps `~/.t3-mini/data`, and dev keeps `.data`.

All commands, how they work, and what's planned (updates for copied binaries, start at login): [docs/t3mini.md](docs/t3mini.md).

### Machines

Use t3 mini on another computer (a VPS, another Mac) from this one: install `t3mini` there (with Claude/Codex signed in and Tailscale on the same tailnet), get a pairing link there with **Settings → Machines → Add this computer to another t3 mini** (or `t3mini pair` in a terminal), and paste it into **Settings → Machines → Add machine** here. Its projects and threads then appear in this sidebar with a machine tag (the hub): open them here, send, stop, approve, and start new threads or add projects on it (**Add project → On:**, creating the folder if it's missing). **Open** still shows that machine's whole t3 mini in a new tab; its agents and files stay on that machine. This Mac keeps the machine's session to itself and the machine sees it as one more paired device (revoke it there under Settings → Devices). See [docs/machines.md](docs/machines.md).

Open **http://localhost:4016** (dev; the installed `t3mini` is on 4011). Click **Add project** (folder-plus icon in the sidebar header) and choose a folder with **Browse…** (the native macOS folder chooser) or enter an absolute or `~/` path; it starts at your home folder (`~/`), and if the folder doesn't exist yet, **Create it and add** makes it (inside your home folder only). Adding a project opens a new thread in it with your last agent and settings, so you can send a message right away. Later, click **New thread** (pencil icon, or ⇧⌘O) to start another: the dialog lists **No project** first (a chat in its own folder, see below), then your projects with their icons: the one you're in (marked **Current**) and the rest by most recent activity. Type to filter by name or folder, ↑/↓ to move, and Enter (or a click) starts the thread right away; Enter on its own starts a chat without a project, and ↓ Enter starts one in the current project. **Add project…** is at the bottom. Enter sends; Shift + Enter inserts a line break. The composer is deliberately simple: **+** attaches images or files, the **model pill** (e.g. “Opus 5.5 Medium”) opens one menu with **Claude | Codex** tabs and a row for each setting: **Model**, **Effort**, and for Codex **Service tier** (Standard or Fast, as reported by Codex). Hover or click a row to open its choices beside the menu; picking one updates the row and keeps the menu open, so you can set the model and then the effort in one go. With Provider default, Effort offers the default model's levels. Clicking the other agent's tab switches the thread to that agent right away, with the model, effort, and tier you last used for it, and the menu stays open on its settings, so going back and forth never means picking again. This works in a started thread too (see **Switching agents mid-thread** below). Choices are remembered per agent (shared across your browsers), and the **lock** button sets the permission mode. Send is the round button on the right; it becomes Stop while the agent works. Like Claude Code, pressing **Esc twice** also stops it: the first Esc shows “Press Esc again to stop”, and a second within a second stops the turn (an Esc that closes a menu or dialog, cancels an edit, or clears picked threads doesn't count). New threads start with your last choices, and open instantly: the agents' model lists are loaded when t3 mini starts and kept for an hour (refreshed in the background), so creating a thread never waits for a CLI; if a saved effort level turns out not to be supported any more, the thread falls back to Default. Model, effort, permissions, and the agent itself can change between any two messages.

**Switching agents mid-thread.** Claude and Codex can't read each other's sessions, so a switch doesn't move the session. Instead, the agent taking over gets a **recap** of the turns it missed in front of your next message: your messages, a work line when there is one, and the other agent's final answers (the newest turns that fit in about 24,000 characters; for older ones it's told it can call `read_thread` on the thread itself). Both agents work in the same folder, so files and git state carry over as they are. The old agent's session is kept: switch back and it resumes its own memory, with a recap of only what happened since. A **Switched to Codex** line marks the switch in the conversation. You can't switch while an agent works or waits on you, the old agent's to-do list is cleared, and edit-and-resend only works for turns the current agent ran. See `src/server/handoff.ts`. Selections are saved per thread and apply to the next message; the settings controls are disabled while an agent is working.

You can keep typing while an agent works: **Enter steers it**. Claude takes the message into the running turn at its next step; Codex receives it via `turn/steer`. If the agent can't take it right then (still starting, between turns, or the provider refuses), the message is marked **Queued** and sent automatically as the next turn. Queued messages from a stopped turn stay in the conversation marked **Not sent**. In an empty composer, **↑** brings back your previous messages (with their images) and **↓** goes forward again, like a shell; the arrows only do this while the recalled text is untouched, so they never get in the way of editing. Hover your last message (once its turn has ended, finished, stopped, or failed) for **Retry** and **Edit** next to its time and copy button. **Retry** runs the same message again right away; **Edit** opens it in the composer in **edit mode**: change it and press Enter to resend it _in place of_ that turn. After you **Stop** a turn (or it fails), ↑ in an empty composer opens it in edit mode too (after a finished turn, ↑ only brings the text back for a new message). Either way the old message and its reply are removed and the agent's own memory is rewound to before that turn (Claude resumes the session from that point; Codex reverts the turn), so it never sees the earlier attempt. Files that turn already changed stay changed. Only your latest message can be retried or edited, and only for turns the current agent ran. Esc cancels editing. If the agent can't rewind, the edit is still sent, as a follow-up, and marked as such. Highlight text in the conversation and a small bar appears above it: **Add to chat** quotes it at the end of the composer (as a Markdown `>` quote, with the cursor on a new line under it), so you can ask about exactly that part; **Ask** sends the quote with a ready question (**Explain this**, **Why?**, **Is this right?**) in one click (with something already in the composer, the quote and question are added there instead of sent); and the copy button copies it (on phones too). Rest the pointer on a thread in the sidebar for a moment to see a **hover card** with a quick look at it: its agent, model, effort and access, status and project, how many messages it has, when it started and was last updated, what it's waiting on (or why it failed), and short excerpts of your latest message and the latest reply. It's fetched from the server when it opens and closes as soon as you move away. **⌘K (Ctrl+K)**, or the search button in the sidebar header, opens a command palette: type to jump to any thread by its title or project name (all words must match), and after two or more characters it also searches inside conversations and lists matching threads under **In messages** with a short excerpt (one per thread, up to 20, searched on the server). With nothing typed it shows your recent threads. Each result shows its project and the same time and status as the sidebar (e.g. `3m`, `2d`, the working dots, or Question/Approval while it waits for you), with unread threads in bold. It searches every project, even while the sidebar shows just one. It also runs a few commands (New thread, Add project, Show/Hide sidebar, Settings). ↑/↓ move, Enter opens, Esc closes. ⇧⌘O (Ctrl+Shift+O) opens a new thread, ⌘S (Ctrl+S) hides or shows the sidebar (also the panel button in the sidebar header; the choice is remembered). Drag the sidebar's right edge to make it wider or narrower (13–30rem, arrow keys work too when the edge is focused); the width is remembered, and double-clicking the edge puts it back to the default, just like the Changes panel's edge. The **+** next to a project in the sidebar starts a thread there in one click with your last settings. Above the list, **All projects** is a menu that narrows the sidebar to one project's threads: open it, type to find a project, and pick it with a click or Enter (pick **All projects** to see everything again). The choice is remembered in each browser, and opening a thread from another project (⌘K, New thread) shows all projects again so that thread isn't hidden. The view-options button (a settings icon) that appears when you hover that line sets **Group by**: **Project** (the default), **Date**, which splits the Recents list below into **Today**, **Yesterday**, **This week** (the rest of the last 7 days), and **Older** by when you last wrote in each thread (click a section's heading to fold it, a chevron shows on hover; only the newest section with threads starts open, **Today**, or **Yesterday** when nothing is from today, and the rest start folded; folds you choose are remembered in each browser), or **None**, which shows every thread in one **Recents** list, newest message first, each on two lines: its project's icon and name, then its title; the choice is saved on the t3 mini server, so every browser, profile, window, and phone shows the same and switches together. A thread's time in the sidebar also shows its state: a spinner while the agent works, **Question** or **Approval** while it waits for you, **Done** (green) or **Failed** (red) when a turn ended while you weren't looking (until you open the thread, then it's the time again), and a red time after a failure. Grouped by project, each project shows its own icon (a favicon or app icon found in the project, e.g. `public/favicon.svg`) or, without one, its first letter in its own color on a soft tint of it, in the sidebar, the chat header's project chip, and the New thread list (turn this off under **Settings → Appearance → Project icons** to get folder icons back); projects stay in a fixed order in the sidebar, newest added on top, so activity never reshuffles them; only the threads inside each project move, by your latest message. After you send a message or start a thread, the sidebar scrolls to show that thread at its new spot in its project, even if you'd scrolled far down (scrolling it yourself right after cancels that). Attach images (up to 10 per message; other formats such as iPhone HEIC are converted, and large photos are scaled to 2048px and about 4 MB on your device before upload) by pasting, dropping them anywhere in the window, or with the **+** button; they're sent to the agent as image input. Dropping any other file inserts its path into your message: the original path when the drag provides one (editors, terminals), otherwise the path of a copy saved under `.data/attachments/files` (browsers don't reveal Finder paths), up to 25 MB. Pasting more than 10,000 characters of text (logs, stack traces, whole files) attaches it as a **Pasted text** file instead of filling the composer: it shows as a chip with its size above the composer (remove it with its ×), is saved under `.data/attachments/files`, and reaches the agent as a `Pasted text: <path>` line at the end of your message, which it reads like any other file. That keeps big logs within the 100,000-character message limit. If the project is a git repository, its current branch appears under the composer; it refreshes when you open the thread, after each turn, and when you return to the window. When the remote is on GitHub, click the branch to open it there in a new tab (the branch it tracks, or the repository on `origin` when it doesn't track one yet). The link comes from the git remote URL, so it needs no `gh` CLI, and any credentials in that URL are never sent to the browser. If the branch has an open pull request on GitHub, a **#number** link next to it opens the pull request in a new tab. t3 mini finds it by matching the branch's pushed commit against GitHub's pull-request refs with `git ls-remote` and your normal git login (SSH or HTTPS), so private repositories work too, with no `gh` CLI or token; the list is fetched at most once a minute per repository. Merged and closed pull requests don't show (GitHub keeps a pull request's test-merge ref only while it's open), so an open pull request with merge conflicts may not show until they're resolved. The default branch (e.g. `main`) never shows one. If VS Code is installed (the `code` command, or on macOS the app in `/Applications`), a VS Code button in the chat header opens the thread's project folder in it. Set `VSCODE_BIN` to use a different `code` executable. In a git project, the **Changes** button in the header (or ⌘D / Ctrl+D) opens a panel with the project's uncommitted changes (tracked files against `HEAD`, plus new untracked files) in **Inline** or **Split** view. It refreshes automatically: as the agent finishes each step, and for changes made anywhere else (your editor, a terminal, git) via a lightweight check every 2 seconds while the panel is open and the tab is visible. The refresh button forces a reload. Files start collapsed (click one to open it, or use expand-all), and the files you open are remembered per project; big change sets are capped: at most 200 files are shown (the header says “200 of N files”), and a file with more than 3,000 changed lines shows its counts without its lines. Whether the panel is open is remembered per project. The panel runs full height beside the chat; drag its left edge to resize (double-click to reset, arrow keys work too), and use the collapse/expand-all button in its header. The browser tab is named after the open thread and its project (e.g. `Login bug · my-app — t3 mini`), with **●** in front while the agent works and **?** while it waits for your approval or answer, so you can tell tabs apart; it follows renames and the AI title. Opening a thread puts the cursor in the composer. When nothing else is focused, typing or pasting anywhere in the window goes straight into the composer, which also works with dictation apps that paste their text.

New threads are named from your first message, then get a short AI title: Claude threads use the title Claude Code writes for its session (the same one Claude Desktop shows, at no extra cost), picked up as soon as Claude starts replying rather than when the turn ends, and Codex threads get one from a quick `gpt-6-luna` call (low effort, fast tier) in a throwaway Codex thread with no tools, which is also saved as the thread's name in Codex. A title you or the agent set is never replaced. Right-click a thread in the sidebar (or use its **⋮** button, shown on hover and always on touch screens) to **Rename** it (or double-click its name), **Regenerate title** (a fresh AI title from the conversation: Claude Haiku for Claude threads, Luna for Codex), start a **New thread in** its project (right away, with your default agent settings, like the project's **+** button), open **Project settings…**, **Copy link** (paste it into another thread and that thread's agent can read this one with `read_thread`: your messages, its final answers, and what the work touched; it only reads threads whose link or ID you wrote in that conversation, from any project, plus its own thread for turns a switch recap left out, and treats them as background, not instructions), copy its project path, or **Delete** it. Renaming works while an agent is running; deleting requires stopping it first. Deleting the thread you have open opens the next one instead of an empty screen: the most recent thread left in the same project, or else the most recent one (within the sidebar's project filter). To act on several threads at once, **⌘-click** (Ctrl-click on Windows/Linux) threads to pick them, **Shift-click** to pick a range, or right-click → **Select** (on a phone, then tap more); while threads are picked, a click toggles them instead of opening them. A bar at the bottom of the sidebar shows how many are picked, with **Delete** (one confirmation for all; threads still running are kept) and **Cancel** (or press Esc). Right-click inside a selection to delete it too. Middle-click still opens a thread in a new tab. Click a project to collapse or expand it, or use the collapse/expand-all button next to **Projects** (collapsed projects are remembered; search still shows matching threads inside them). Right-click a project to start a thread there right away, **Rename** it, open **Project settings…**, copy its path, or **Remove** it from the sidebar. **Project settings** (also on a thread's right-click menu, so it works in the Recents view too) sets the project's name and its avatar: **Automatic** (the project's own favicon or app icon, else its letter), **Letter**, or **Image** (upload your own: PNG, JPEG, GIF, or WebP, checked from the file itself; square images look best). A project with threads can be removed together with all of them in one go: a confirmation says how many threads will be deleted, and it's refused while any of them is running. Files on disk are never touched. Renaming changes only the name t3 mini shows (in the sidebar, header, and New thread dialog), never the folder; clear the name to go back to the folder name.

Use the sun/moon/monitor button at the bottom of the sidebar to cycle between Light, Dark, and System themes, or pick one under **Settings → Appearance**. System follows your OS setting.

When a thread finishes, a soft sound plays (pick Soft chime, Marimba, or Pop, or turn it off, under **Settings → Notifications**). A thread that finishes or fails while you aren't looking at it gets a bold title in the sidebar until you open it (unread is shared: the t3 mini server marks a thread unread when it finishes or fails while you aren't looking at it in any tab, browser profile, or phone, and opening it anywhere clears it everywhere). When a thread finishes, fails, stops, or needs approval, a toast appears in the corner. Click it to open that thread. On your first visit, t3 mini offers to turn on desktop notifications, which fire while the window is in the background. They name the project, the agent, and what happened (e.g. “t3-mini · Claude finished”), with the thread's title underneath. Each thread keeps one entry in Notification Center, and a newer notification for the same thread still pops up instead of silently replacing the older one. With t3 mini open in several tabs, browser profiles, or on your phone, only the tab you used last, across all of them (the t3 mini server keeps track), sends the desktop notification, plays the sound, and plays background music, and only when you aren't on that tab; each tab still shows its own toasts. Enable or disable desktop and in-app notifications at any time from **Settings** (gear icon at the bottom of the sidebar). If you blocked notifications in the browser prompt, allow them in your browser's site settings for localhost, then reload.

t3 mini keeps some settings **shared** and some **per device**:

- **Shared by every browser, profile, window, and phone** (saved on the t3 mini server in `.data/ui.json` and switched live in every open window): the theme, Project icons, Working animations, Group by, collapsed projects, your last agent and per-agent model, effort, and permission choices (so new threads start with them), and Working background music (on/off, link, volume, and where the song was). Each browser also keeps a copy so they apply instantly on load; the first time a browser opens after an update, any of these it had and the server didn't are carried over.
- **Per device** (this browser's `localStorage`): notifications and sound (desktop notifications need each browser's own permission), the sidebar's width and whether it's hidden, the Changes panel, drafts, unread markers, and the dictation microphone.

Install and sign in to the providers you want to use:

```sh
# Codex
npm install -g @openai/codex
codex login

# Claude Code (macOS / Linux)
curl -fsSL https://claude.ai/install.sh | bash
claude
```

Claude runs through the Claude Agent SDK using your installed `claude` CLI (`CLAUDE_BIN`, else `claude` on PATH or in `~/.local/bin`), so updating Claude Code updates t3 mini too; without a CLI, the SDK's bundled runtime is used. Both agents use your local provider credentials. The **Settings → Agents** section (a warning icon appears in the sidebar footer when a CLI is missing) reports whether a standalone `claude` / `codex` command is available, its version, and the account each agent is signed in with (e.g. “Signed in · Claude Team”, “· ChatGPT Pro 5x”; the email stays hidden until you click the eye button next to it), as the agents themselves report it (Claude's SDK account info, Codex's `account/read`; no AI call, no token read, cached for five minutes). It does not check account limits. Restart the server after installing a CLI or changing environment settings.

### Agent updates

On the Mac, t3 mini checks npm for new Claude Code and Codex releases (at startup and every six hours). When one is out, a card at the bottom of the sidebar shows the version change with an **Update** button, which runs `claude update` or `codex update` in the background. The next turn uses the new version, and existing threads resume as before. Updating waits until no thread on that agent is running. Hiding the card skips that version in this browser. Phones never see it.

## What it does

- Saved threads, independent provider sessions, and project folders. Each thread has a `/threads/<thread-id>` URL, so refresh, direct links, and browser Back/Forward preserve selection.
- Provider-supplied model pickers, model-specific effort levels, and saved permission modes.
- Threads without a project: pick **No project** in the New thread dialog (or "New thread without a project" in ⌘K) for a chat that isn't about one of your projects, like T3 Code's. It works in a folder of its own under `~/.t3-mini/chats`, named from the date and your first message (e.g. `2026-10-21-fix-my-resume-a1b2c3d4`), so anything the agent makes stays together; these threads show under **No project** in the sidebar. Deleting one removes its folder if it's empty; files the agent made there stay.
- Worktree threads: in a git project, pick **New worktree** under the composer before the first message and the agent works in its own checkout on a new `t3m/…` branch (in `~/.t3-mini/worktrees`), so your main checkout and other threads aren't touched. Files listed in `.worktreeinclude` (e.g. `.env`) are copied in, and a listed folder such as `node_modules/` is cloned whole (copy-on-write on macOS, no extra disk space), so dependencies are ready without an install. Deleting the thread removes a clean worktree at once (the branch stays). Creating one takes tens of milliseconds for a typical app. See [docs/worktrees.md](docs/worktrees.md).
- Lead and helper threads: ask a thread to split work up ("start two helpers: one adds dark mode, one fixes the login bug") and it starts helper threads, Claude or Codex, each in its own worktree. They report back to the lead automatically when they finish, and the lead can message, list, stop, and delete them. Helpers are normal threads you can open. See [docs/orchestration.md](docs/orchestration.md).
- Agents can show images in the chat (Claude, and Codex threads created from now on): ask “take a screenshot and show me” or “show me the chart you made”. They use t3 mini's `show_image` tool, which only accepts real image files inside the project or temp folder. See [docs/tools.md](docs/tools.md). Click any image in a thread (yours or the agent's) to preview it full screen; **← / →** (or the arrows at the sides) step through the thread's other images, with an "N of M" counter.
- Agents can use a browser to check their work (Claude, and Codex threads created from now on): ask “start the dev server and check the login page”, “click through sign-up and tell me what breaks”, or “screenshot the page on a phone size in dark mode”. The agent opens the page in its own invisible browser (your installed Google Chrome, Microsoft Edge, Brave, or Chromium; nothing is downloaded), reads it, clicks and types, works with several tabs (pages that open a new tab or window become tabs it can switch between, up to 5), waits for things to load or redirect, checks the console for errors and failed requests, and takes screenshots of the page or a single element, sharing them in the chat when useful. To test as a signed-in user it can set a login cookie for a local site (the value never shows in the chat). For safety it can only open **local sites**: localhost, 127.0.0.1, *.localhost, and local development domains such as Laravel Herd/Valet's `app.test` (or `.local`, `.internal`, `.home.arpa`, `.lan`) when they resolve to your Mac; never t3 mini itself, and it can't run scripts in the page, upload files, or download. To let it open **public websites** too (like Claude Desktop's browser), turn on **Settings → Agents → Open public websites** (off by default): public sites are read-only for the agent (it can look, click, and take screenshots, but not type or press keys there), and it still can't reach your local network or tailnet. Each thread gets a private session with no cookies or logins from your own browser. Opening or checking a local page needs no approval (it only loads the page); clicking, typing, key presses, and login cookies follow the thread's permission setting (no prompts with Full access). Agents are told about the browser (gently: they check visible changes when it seems worth it), **browser_check** looks at a page in one step (a screenshot, the page, and any console errors or failed requests), the dev server they started opens without typing its address, and every open or click reports problems on the page right away. **Settings → Agents → Browser checks** shows how often each agent checked its UI changes in the browser (of the finished turns that changed components, pages, or styles; counts only, in `.data/browser-stats.json`). You can tell when it's browsing: browser steps have a 🌐 globe and name what they act on ("Click button 'Sign up'" instead of a raw reference), the live working line shows the site ("Click button 'Sign up' · localhost:5173"), and while the thread's browser is open a **🌐 localhost:5173** chip sits next to the processes indicator under the composer. Click the chip for the page's title and address, a live preview (refreshed every few seconds), and **Close browser**. See [docs/browser.md](docs/browser.md).
- Agents can draw diagrams in the chat, like Claude Desktop: ask “draw the login flow”, “show the database schema as a diagram”, or “sketch the architecture”. They write Mermaid (flowcharts, sequence, state, class and ER diagrams, Gantt charts, mind maps, timelines, pie charts and more) through t3 mini's `show_diagram` tool, and the chat draws it right in the reply, without a frame, in the light or dark theme. A quiet row under it (shown when you hover, always on touch screens) has its title, **Diagram / Code** views, a copy button for the Mermaid source, and **Expand** (or click the diagram) for a full-screen view with zoom and **Download SVG**. Diagrams never scroll inside the reply: wide ones shrink to fit, and a left-to-right flowchart that would shrink below 70% is drawn top to bottom instead, so it stays readable. A reply that contains a ` ```mermaid ` code block is drawn the same way (it stays a code block while it streams in, or if it isn't valid Mermaid). Codex threads created before this feature don't have the tool, but their ` ```mermaid ` blocks still draw.
- Agents can show small interactive HTML pages in the chat (charts with buttons, sortable tables, UI mockups, calculators) with t3 mini's `show_html` tool: ask “make me an interactive chart of this” or “mock up this screen”. The page runs in a sealed sandbox: its own origin (no access to t3 mini, its storage, or its API), no network, popups, forms, or navigation; it follows the light or dark theme and sits right in the reply, without a frame, as tall as the page (it never scrolls inside). A quiet row under it (shown when you hover, always on touch screens) has its title, **Reload**, **View source**, **Copy HTML** and **Expand**. See [docs/tools.md](docs/tools.md#show_html) for the security details.
- Agents can show videos and play sounds in the chat: ask “record a short demo and show me” or “say the summary out loud”. `show_video` shows MP4, WebM, MOV, or Ogg video with play controls (seeking works, also on a phone); `play_audio` shows MP3, M4A, WAV, Ogg, FLAC, or WebM audio in a player. Neither starts on its own: you press play. Files are checked by their contents, copied into `.data/attachments/media`, and limited to the project or temp folders (videos up to 200 MB, sounds up to 50 MB).
- Agents can rename their own thread: ask “rename this thread to Login bug” or “give this session a better name”. They can't rename other threads. (Codex threads created before this feature don't have it.)
- Agents can run long-lived processes such as dev servers (“start the dev server”): a **● N running** indicator under the composer lists them with their URL, live **Logs**, **Restart**, and **Stop**. They stop when t3 mini stops. Starting one asks for approval unless the thread has full access.
- Links in your own messages are clickable too (`http`/`https` addresses only, opening in a new tab like links in replies).
- Streamed Markdown replies (code blocks have a copy button; hovering your messages and the agent's final answers shows the time and a copy button that copies it as written, Markdown included, like Claude Desktop).
- Turns read like Claude Desktop. While the agent works, its work so far is folded behind **one working line** that shows the agent's latest note in its own words, whole rather than word by word as it streams (a note appears once its paragraph is finished; until then, the one before it or what it's doing now), how long the turn has run, and **"N steps ›"**; click that to open everything so far: its in-between notes in the order they happened, and each run of steps between two notes as one line that updates to the latest step (e.g. "Print working directory · 5 steps ›"; click it to see them all), like Claude Code. Opening it is remembered for that turn. A to-do checklist stays in view either way. Browser steps name what they touched in words (**Click "Finish game" in the dialog**, not the raw selector), and steps the agent retried and got past show as "· 2 retried" in gray; red is kept for runs that ended on a failure. The working line shimmers while the agent works and is led by an animated Claude or Codex character that matches what it's doing (thinking while it starts up or decides what's next, working while a step runs) and that celebrates for a few seconds when the turn finishes; turn the characters off under **Settings → Appearance → Working animations** to get the simple dots. **Working background music** (off by default, under **Settings → Music**) plays a YouTube video or playlist you paste, such as a lofi stream, while any agent is working, fading in and out and picking up where it left off, even after a reload or in another tab (live streams just play live); there's no visible player (while it plays, a Claude or Codex character holding a radio, matching the open thread's agent, sits at the top left of the chat), and only one song plays however many agents or t3 mini tabs there are (in the tab you used last). It uses a privacy-enhanced `youtube-nocookie.com` embed controlled with YouTube's embed messages (YouTube's script is never loaded into t3 mini), loaded only once music is first needed; browsers only allow sound after you've clicked or typed in the page, and ads in the video play too (they're also replaced by the dots when your system's Reduce motion is on) (e.g. "List the project folder 12s"). When the turn finishes, that work folds into one line, **Worked for 2m 10s · 12 steps ›**, above the final answer (**Stopped after…** / **Failed after…** when it ended early); click it to see everything again. If the agent answered and then added more once background work it left running finished (e.g. "the full test suite passed"), both of those replies stay in view, in order; only the work before them folds. Under the latest turn, once it's done, a wavy line marks the end of the thread with how long it took and when it finished, like Claude Code: **Worked for 24s · done 2:00 PM** (or **Stopped after…** / **Failed after…**; the date is added when it wasn't today). When the agent keeps a to-do list (t3 mini's `update_checklist` tool, which both agents are told to use for multi-step work; or Claude's own to-do tools, which t3 mini turns on for its Claude sessions, or Codex's plan), it shows as a **checklist card** that updates in place: done items are checked, the current one spins, the rest wait; between steps the live line names the current item ("Running the tests"). Each turn keeps its own checklist: a new turn starts without one, and opening an older turn's **Worked for…** line shows the list as that turn left it. The card folds away with the rest of the work when the turn ends, unless items were left undone: then it stays in view and the line says so (**Stopped after 1m · 4 steps · 2 of 6 left**). A subagent's own to-do list never replaces the thread's. When the agent pushes to GitHub, opens a pull request, deploys, or runs another long step, it can show a **status card** (`show_status`) that stays in view under the working line while the work is folded and updates in place: a moving bar while it runs, stages like Build › Upload › Live, the commits pushed, then **Done**/**Live** with a link, **Failed** with the error lines, or **Didn't finish** if the turn ended first. Images, diagrams, and status cards the agent showed you along the way (e.g. screenshots from `show_image`, diagrams from `show_diagram`) don't fold away: they move into the final answer, above its text, in the order they were shown, so the results stay in view and an answer that says "the diagrams above" reads right. Each step is one line: Claude's own description of a command when it gives one ("Build the package and run the tests"), otherwise like `Run git status`, `Read src/app.ts`, or `Edit src/styles.css`, with **Failed** when it failed; click a step to see the full command or edit and its output (long output is trimmed). Steps are kept for the latest run only, so older turns fold just the agent's notes ("· 3 messages"), and steps saved before this layout show after that turn's notes.
- Long threads open instantly: only the latest turns are drawn at first, and older ones are added as you scroll up. Switching back to a thread returns you to where you were in it (in that tab), or to the bottom if that's where you left it.
- The chat follows new output while you're at the bottom; scroll up and it stays put, with a round **↓** button above the composer to jump back to the latest message (and follow again).
- When the agent compacts the conversation (its context got long, or you sent `/compact`), the live line says **Compacting the conversation** with a squeezing-lines icon, and afterwards a divider in the turn's steps shows how much it shrank (e.g. "Conversation compacted · 39k → 2.4k tokens · automatic · 10s", with a small before/after meter; Codex doesn't report token counts) or why it failed. The folded turn line adds "· compacted".
- Real provider status: starting, working, waiting for approval, completed, stopped, or failed. While the open thread's agent is starting or working, a thin bar swings left and right along the bottom edge of the thread's header, like a terminal's progress bar (a gentle pulse with Reduce motion; hidden while it waits on you).
- Explicit **Allow once / Decline** actions when a provider requests tool approval, plus **Stop** for an active turn. Stop is instant, like Claude Desktop: the thread shows as stopped right away (in every tab) while the agent winds down in the background (Claude ends the turn cleanly with an interrupt, and is killed only if that takes more than a few seconds). A message you send right after waits for that, then starts a fresh turn.
- When Claude or Codex asks you a multiple-choice question (Claude's AskUserQuestion tool, or t3 mini's `ask_user` tool for Codex, which otherwise could only ask in plain text and stop), a slim question card shows the question on one line and each option on its own line, its description trailing in grey (wrapped underneath on phones), with a **Recommended** badge on the agent's suggestion. One click, or the option's number key (when you're not typing in a text field), answers a single-choice question; a multi-select question lets you pick several, then **Next** or **Send**. Several questions come one at a time ("1 of 3", with **Back**) and are sent together after the last. Type in the **Something else…** row for your own answer and press Enter; **Skip** lets the agent carry on without. Sending a message from the composer instead answers the question too, as your own answer ("Something else"); it shows in the chat marked _Answered the question_. Questions appear in every permission mode, including Full access, since they need your answer rather than your permission.
- Work Claude leaves running in the background (a background subagent or shell) keeps the turn open after its last reply; a **Still running in the background** line names it until it finishes, and a subagent's steps are tagged with its task name.
- Live updates over Server-Sent Events, including reconnect snapshots. Each tab gets only the parts that changed (the full snapshot on connect), so another thread streaming doesn't resend the long thread you're reading. Switching threads or closing the browser does not stop an agent.
- Recoverable conversations after a server restart. A turn that was active at restart appears as stopped; send a new message to resume its provider session.

Completion comes from the provider's turn result, not from text matching or an inactivity timer. A completed turn means the provider finished responding, not that the requested work was independently validated.

Model catalogs come directly from the local providers and are cached for five minutes. Effort choices follow the selected model’s capabilities (the provider's default model when Provider default is selected). Switching models resets effort to Default. Catalog availability does not guarantee account access. If loading fails, Provider default remains available and the picker offers Retry.

## How it works

```text
Browser → TanStack Start server routes → AgentService
                                       ├─ Codex app-server (JSON-RPC over stdio)
                                       └─ Claude Agent SDK (query + streamed events)
Browser ← Server-Sent Events ← saved thread state
```

Permissions map to each provider’s native modes:

| Mode              | Behavior                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| Approval required | Codex starts read-only and requests approvals for untrusted actions; Claude uses its default permission checks.  |
| Auto-accept edits | Codex allows workspace writes; Claude automatically accepts project edits. Other actions may ask for approval.   |
| Auto              | The provider reviews actions automatically. Availability depends on your provider, model, and account policy.    |
| Full access       | Codex removes its sandbox; Claude bypasses normal permission prompts. This permits actions outside your project. |

New threads default to **Claude** (Codex if only Codex is installed) and **Full access**; once you pick something else, your last choice is used instead. Full access lets the agent run any command and edit files outside your project without asking — use it only with projects and machines you trust, and switch to Approval required for anything sensitive. Threads saved before permission modes existed keep their original mode (Codex: Auto-accept edits; Claude: Approval required). Claude reads your user/project/local settings. Existing provider settings can already allow some tools; approvals appear when the provider asks for them. Neither integration installs a plugin. Provider login stays outside this app.

The **Browse…** chooser opens on the Mac running the server. Cancel leaves the current folder unchanged. On other operating systems, enter the project folder path manually.

This first version runs on one local Node process. It binds to loopback and rejects foreign hosts and cross-origin API requests. Phone access (below) is the only way in from another device. There are no tunnels or checkpoint rollback. Use a project folder you intend the agent to edit, or a worktree thread (above) to keep it apart from your checkout. Decline unsupported requests or stop the turn and answer with a follow-up message.

## Dictation

The 🎤 button in the composer records your voice and types the transcript at the cursor: click to record, click again to stop (recordings stop on their own after 5 minutes). Transcription is live: while you speak, the words so far appear in the empty composer's placeholder (the composer grows to fit them; once it's full, the newest words stay in view), and when you stop, the final text is inserted at the cursor. A short sound plays when recording starts and stops; turn it off under **Settings → Dictation → Recording sounds**.

To spell names and code terms right, dictation also uses the thread's vocabulary: the server picks up to 40 unusual words from the agent's last two replies (names like _Deepgram_, identifiers like `useState`, acronyms, and words outside a standard English word list) and sends them to Deepgram as [keyterms](https://developers.deepgram.com/docs/keyterm) with your audio. It never takes them from your messages, code blocks, links, or email addresses, and drops anything that could be a key or token (long or random-looking strings, digits, hex, key prefixes such as `sk-` or `ghp_`). The browser only says which thread you're in; the words are chosen on the server. Turn it off under **Settings → Dictation → Use words from the thread**. Keyterms need a Nova-3 or Flux model, so they're skipped if `DEEPGRAM_MODEL` is set to another one. Transcription uses [Deepgram](https://deepgram.com) (`nova-3` with smart formatting); new Deepgram accounts get free credit, then it's pay-as-you-go.

1. Create an API key at [console.deepgram.com](https://console.deepgram.com).
2. In t3 mini, open **Settings → Dictation**, paste the key, and click **Save**. The server checks it with Deepgram first.
3. Optionally pick a **Microphone** in the same tab (after allowing microphone access once, so the browser shows device names). The choice is remembered per browser and falls back to the system default if that microphone is unplugged.

The key is stored on the Mac in `.data/secrets.json` (owner-only, gitignored) and is never sent back to the browser; Settings shows only its last four characters. Alternatively set `DEEPGRAM_API_KEY` in the environment or in a `.env` file (see `.env.example`), which takes priority. The key can only be viewed or changed on the Mac, not from a paired phone. Audio streams from the browser to the t3 mini server over a local WebSocket (`/api/dictation/stream`, same-origin only) and from there to Deepgram's live API, with Deepgram's model-improvement program opted out (`mip_opt_out=true`). Only the transcript text comes back to the browser. If streaming can't connect, the finished recording is sent to `/api/transcribe` instead, so dictation still works, just without the live preview.

Browsers only allow the microphone on secure pages, so the button appears on the Mac (`localhost`) but not over plain-HTTP access from other devices; use the device keyboard's dictation there.

## Devices: use t3 mini on another computer, a tablet, or your phone

Run t3 mini on one computer and use it from any other device's browser: your MacBook, a tablet, or your phone. They all see the same threads live. Connect either on the same Wi-Fi (**Local network**) or from anywhere over **Tailscale (HTTPS)**. It's off by default. After the server restarts, **Tailscale** access you left on comes back by itself so paired devices reconnect without pairing again (**Reconnect after restart**, on by default; it keeps trying for about 9 minutes while Tailscale starts up). **Local network** access always turns off on restart, since the Mac may be on a different network by then.

1. On the computer running t3 mini, open **Settings → Devices**, pick a **Connection**, and turn on **Allow other devices**. A devices icon appears in the sidebar footer while it's on.
2. Click **Connect a device**. On a phone or tablet, scan the QR code with the camera. On another computer, click **Copy link** and open the link in that computer's browser (send it to yourself however you like: AirDrop, Messages, a note). The link opens a **Connect this device** page; press the button to pair (opening or previewing the link alone doesn't use it up, so sharing it over iMessage is fine). The code works once and expires after 5 minutes, and anyone who has the link before then could pair, so only open it on your own device.
3. Each device stays paired for 30 days and is listed by type (e.g. "iPhone · Safari", "Mac · Chrome"). Revoke one device or all of them in the same section; revoking cuts open connections immediately.

Other devices see the same threads live, and can send, steer, approve, stop, and view changes. Actions that belong to the computer running t3 mini (Browse for a folder, Open in VS Code, managing access) are hidden on other devices and refused by the server.

**See your dev server on the device (preview, early).** When an agent runs a dev server on the computer (`localhost:3000`), open the **● running** list on the phone or tablet and tap **Open :3000 on this device** (one button per address the dev server printed, e.g. a website on :3000 and its API on :3001). Tapping a `localhost` link in the chat (an agent's "running at http://localhost:3000/login") does the same and lands on that page. t3 mini gives that dev server its own address next to t3 mini's, its port + 10000 (`https://<this Mac>.<tailnet>.ts.net:13000` over Tailscale, `http://<LAN address>:13000` on the local network), and forwards to it as if you were on the computer: pages, live reload, sign-in redirects, and cookies work without changing your project. Only paired devices get in (the button hands the device a one-time pass that becomes a cookie for that address), only dev servers t3 mini started can be shared, and t3 mini's own login never reaches your app. A preview closes when its dev server stops or access is turned off. Your app's own code that calls `http://localhost:3000` directly, and "Sign in with Google/GitHub" (the provider sends you back to the address registered with it), still need that address configured.

**Local network** (plain HTTP): a gateway listens on port `4311` (set `T3_MINI_PHONE_PORT` to change it) only while access is on. It accepts requests only for this Mac's own local-network address, only from private network addresses, only with a paired session cookie (`HttpOnly`, `SameSite=Lax`), and only from its own origin, then forwards them to the loopback-only app marked as remote. Traffic isn't encrypted, so use it only on a network you trust (such as home Wi-Fi), never on public or shared Wi-Fi: anyone who can watch the traffic could take over a paired session, and with it agents that can run commands on this Mac. macOS may ask once whether to allow incoming connections for `node`.

**Tailscale (HTTPS)**: encrypted, and works from anywhere (cellular included) without opening ports. Install [Tailscale](https://tailscale.com) on the Mac and the other device, sign both in to the same tailnet, and turn on MagicDNS and HTTPS certificates in the Tailscale admin console (if HTTPS isn't on yet, Settings shows the link to enable it). t3 mini then runs `tailscale serve` to publish the gateway at `https://<this Mac>.<tailnet>.ts.net:8443` (set `T3_MINI_TAILSCALE_PORT` to change the port) to **your tailnet only**; it never uses Tailscale Funnel, so nothing is on the public internet. In this mode the gateway listens on loopback only, so nothing is exposed on your Wi-Fi either, and the serve entry is removed when access turns off or t3 mini stops (and added again when it reconnects after a restart). Devices still pair with a code (QR or link): being on the tailnet isn't enough on its own. Over HTTPS the device can also use the microphone for **dictation** and the clipboard. Set `TAILSCALE_BIN` if the `tailscale` command isn't on your PATH or in `/Applications/Tailscale.app`.

Session tokens and pairing codes are stored only as SHA-256 hashes in `.data/devices.json`; the reconnect setting and whether Tailscale access was on are in `.data/phone-access.json`. Other devices get in-app toasts and sound for finished threads; system notifications on phones would need a home-screen web app with push, which t3 mini doesn't do yet.

Developer details (architecture, security invariants, pitfalls, tests): [docs/phone-access.md](docs/phone-access.md).

## Data and configuration

Conversations are atomically saved to `.data/threads.json` (while a reply streams, at most once a second; turn ends are saved right away, and a pending save is written when t3 mini exits), projects to `.data/projects.json`, and attachments under `.data/attachments/` (all gitignored). Deleting a thread does not delete its attachments. Creating a thread also saves its folder as a project. Provider session IDs are kept so later messages continue the same conversation. Deleting a thread removes its t3 mini history; the provider may retain its own native session history. Back up `.data` if you need it.

| Environment variable     | Purpose                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `T3_MINI_DATA_DIR`       | Override the `.data` directory.                                                                                                                |
| `T3_MINI_CHATS_DIR`      | Where threads without a project get their folders; defaults to `~/.t3-mini/chats`.                                                             |
| `T3_MINI_WORKTREES_DIR`  | Where worktree threads' worktrees go; defaults to `~/.t3-mini/worktrees`.                                                                      |
| `CODEX_BIN`              | Codex executable path; defaults to `codex` on PATH.                                                                                            |
| `T3_MINI_BROWSER`        | Path to the Chromium-based browser the agents' browser tools use; defaults to Google Chrome, then Microsoft Edge, Brave, or Chromium.          |
| `CLAUDE_BIN`             | Claude Code executable for the SDK, CLI check, and updates; defaults to `claude` on PATH or in `~/.local/bin`, else the SDK's bundled runtime. |
| `PORT`                   | Server port; production (`t3mini`, `bun run start`) defaults to `4011`, `bun run dev` uses `4016`.                                             |
| `VSCODE_BIN`             | Optional `code` executable used by the Open in VS Code button.                                                                                 |
| `T3_MINI_PHONE_PORT`     | Port for other devices on your local network; defaults to `4311`.                                                                              |
| `T3_MINI_TAILSCALE_PORT` | HTTPS port for other devices over Tailscale; defaults to `8443`.                                                                               |
| `TAILSCALE_BIN`          | Tailscale CLI path; defaults to the one inside `/Applications/Tailscale.app`, then `tailscale` on PATH.                                        |
| `DEEPGRAM_API_KEY`       | Deepgram key for dictation; overrides the one saved in Settings.                                                                               |
| `DEEPGRAM_MODEL`         | Deepgram model for dictation; defaults to `nova-3`.                                                                                            |

`bun run dev` and `bun run start` load a `.env` file if present (`t3mini` reads `~/.t3-mini/.env` instead). Use one server process per data directory. Runtime credentials and environment variables are never sent to the browser. Conversations and tool inputs may contain project information, so keep the data directory private.

## Production and checks

```sh
bun run build
bun run start      # Node, port 4011, data in .data (or install the binary: see Install)

bun run typecheck
bun run test
```

The production server (`server.mjs` on Node, or the `t3mini` binary on Bun, both through `app-server.mjs`) serves the built client, SSR, API routes, and event streams on localhost. This app needs a long-running local Node process with filesystem and CLI access; static-only and edge hosting cannot run these adapters.

Tests cover lifecycle transitions, approvals, stopping, concurrent submissions, disk recovery, request origin checks, and the Codex stdio protocol using a local fixture. No paid provider calls are made by the test suite.
