# t3 mini

A small, local coding-agent workspace built with **TanStack Start**, React, and TypeScript. Threads live in the left sidebar; the conversation lives on the right. Choose **Codex** or **Claude Code** for each thread.

## Run

Requires Node.js **22.12+** (or a newer supported Node release) and [Bun](https://bun.sh) as the package manager. The app itself still runs on Node; Bun installs dependencies and runs the scripts.

```sh
bun install
bun run dev
```

Open **http://localhost:4310**. Click **Add project** (folder-plus icon in the sidebar header) and choose a folder with **Browse…** (the native macOS folder chooser) or enter an absolute or `~/` path. Adding a project opens a new thread in it with your last agent and settings, so you can send a message right away. Later, click **New thread** (pencil icon) and pick a project to start another. The new-thread dialog starts on the project you were last active in: the open thread's project, otherwise the most recently active one. Enter sends; Shift + Enter inserts a line break. The composer is deliberately simple: **+** attaches images or files, the **model pill** (e.g. “Opus 5.5 Medium”) opens one menu with **Claude | Codex** tabs and a row for each setting: **Model**, **Effort**, and for Codex **Service tier** (Standard or Fast, as reported by Codex). Hover or click a row to open its choices beside the menu; picking one updates the row and keeps the menu open, so you can set the model and then the effort in one go. With Provider default, Effort offers the default model's levels. Clicking the other agent's tab switches the thread to that agent right away (only before the first message), with the model, effort, and tier you last used for it, so going back and forth never means picking again. Choices are remembered per agent in this browser, and the **lock** button sets the permission mode. Send is the round button on the right; it becomes Stop while the agent works. New threads start with your last choices. Model, effort, and permissions can change between any two messages; the agent can change only until the first message, because a provider session can't move to another agent. Selections are saved per thread and apply to the next message; the settings controls are disabled while an agent is working.

You can keep typing while an agent works: **Enter steers it**. Claude takes the message into the running turn at its next step; Codex receives it via `turn/steer`. If the agent can't take it right then (still starting, between turns, or the provider refuses), the message is marked **Queued** and sent automatically as the next turn. Queued messages from a stopped turn stay in the conversation marked **Not sent**. In an empty composer, **↑** brings back your previous messages (with their images) and **↓** goes forward again, like a shell; the arrows only do this while the recalled text is untouched, so they never get in the way of editing. After you **Stop** a turn (or it fails), ↑ opens your last message in **edit mode**: change it and press Enter to resend it _in place of_ the stopped turn. The stopped message and its partial reply are removed and the agent's own memory is rewound to before that turn (Claude resumes the session from that point; Codex reverts the turn), so it never sees the abandoned attempt. Files the stopped turn already changed stay changed. Esc cancels editing. If the agent can't rewind, the edit is still sent, as a follow-up, and marked as such. Rest the pointer on a thread in the sidebar for a moment to see a **hover card** with a quick look at it: its agent, model, effort and access, status and project, how many messages it has, when it started and was last updated, what it's waiting on (or why it failed), and short excerpts of your first message and the latest reply. It's fetched from the server when it opens and closes as soon as you move away. **⌘K (Ctrl+K)**, or the search button in the sidebar header, opens a command palette: type to jump to any thread by its title or project name (all words must match), and after two or more characters it also searches inside conversations and lists matching threads under **In messages** with a short excerpt (one per thread, up to 20, searched on the server). With nothing typed it shows your recent threads. Each result shows its project and the same time label as the sidebar (e.g. `3m`, `2d`, or Question/Approval while it waits for you). It also runs a few commands (New thread, Add project, Show/Hide sidebar, Settings). ↑/↓ move, Enter opens, Esc closes. ⇧⌘O (Ctrl+Shift+O) opens a new thread, ⌘S (Ctrl+S) hides or shows the sidebar (also the panel button in the sidebar header; the choice is remembered). Drag the sidebar's right edge to make it wider or narrower (13–30rem, arrow keys work too when the edge is focused); the width is remembered, and double-clicking the edge puts it back to the default, just like the Changes panel's edge. The **+** next to a project in the sidebar starts a thread there in one click with your last settings. Projects are listed by your latest message in any of their threads (or when you added them), and deleting threads never moves a project down. The sidebar lists threads by your latest message, so after you send a message or start a thread it scrolls back to show that thread at its new spot, even if you'd scrolled far down (scrolling it yourself right after cancels that). Attach images (up to 10 per message; other formats such as iPhone HEIC are converted, and large photos are scaled to 2048px and about 4 MB on your device before upload) by pasting, dropping them anywhere in the window, or with the **+** button; they're sent to the agent as image input. Dropping any other file inserts its path into your message: the original path when the drag provides one (editors, terminals), otherwise the path of a copy saved under `.data/attachments/files` (browsers don't reveal Finder paths), up to 25 MB. If the project is a git repository, its current branch appears under the composer; it refreshes when you open the thread, after each turn, and when you return to the window. When the remote is on GitHub, click the branch to open it there in a new tab (the branch it tracks, or the repository on `origin` when it doesn't track one yet). The link comes from the git remote URL, so it needs no `gh` CLI, and any credentials in that URL are never sent to the browser. If the branch has an open pull request on GitHub, a **#number** link next to it opens the pull request in a new tab. t3 mini finds it by matching the branch's pushed commit against GitHub's pull-request refs with `git ls-remote` and your normal git login (SSH or HTTPS), so private repositories work too, with no `gh` CLI or token; the list is fetched at most once a minute per repository. Merged and closed pull requests don't show (GitHub keeps a pull request's test-merge ref only while it's open), so an open pull request with merge conflicts may not show until they're resolved. The default branch (e.g. `main`) never shows one. If VS Code is installed (the `code` command, or on macOS the app in `/Applications`), a VS Code button in the chat header opens the thread's project folder in it. Set `VSCODE_BIN` to use a different `code` executable. In a git project, the **Changes** button in the header (or ⌘D / Ctrl+D) opens a panel with the project's uncommitted changes (tracked files against `HEAD`, plus new untracked files) in **Inline** or **Split** view. It refreshes automatically: as the agent finishes each step, and for changes made anywhere else (your editor, a terminal, git) via a lightweight check every 2 seconds while the panel is open and the tab is visible. The refresh button forces a reload. Files start collapsed (click one to open it, or use expand-all), and the files you open are remembered per project; big change sets are capped: at most 200 files are shown (the header says “200 of N files”), and a file with more than 3,000 changed lines shows its counts without its lines. Whether the panel is open is remembered per project. The panel runs full height beside the chat; drag its left edge to resize (double-click to reset, arrow keys work too), and use the collapse/expand-all button in its header. Opening a thread puts the cursor in the composer. When nothing else is focused, typing or pasting anywhere in the window goes straight into the composer, which also works with dictation apps that paste their text.

New threads are named from your first message, then get a short AI title: Claude threads use the title Claude Code writes for its session (the same one Claude Desktop shows, at no extra cost), picked up as soon as Claude starts replying rather than when the turn ends, and Codex threads get one from a quick `gpt-6-luna` call (low effort, fast tier) in a throwaway Codex thread with no tools, which is also saved as the thread's name in Codex. A title you or the agent set is never replaced. Right-click a thread in the sidebar (or use its **⋮** button, shown on hover and always on touch screens) to **Rename** it (or double-click its name), **Regenerate title** (a fresh AI title from the conversation: Claude Haiku for Claude threads, Luna for Codex), copy its project path, or **Delete** it. Renaming works while an agent is running; deleting requires stopping it first. To act on several threads at once, **⌘-click** (Ctrl-click on Windows/Linux) threads to pick them, **Shift-click** to pick a range, or right-click → **Select** (on a phone, then tap more); while threads are picked, a click toggles them instead of opening them. A bar at the bottom of the sidebar shows how many are picked, with **Delete** (one confirmation for all; threads still running are kept) and **Cancel** (or press Esc). Right-click inside a selection to delete it too. Middle-click still opens a thread in a new tab. Click a project to collapse or expand it, or use the collapse/expand-all button next to **Projects** (collapsed projects are remembered; search still shows matching threads inside them). Right-click a project to start a thread there, **Rename** it (or double-click its name), copy its path, or **Remove** it from the sidebar. A project with threads can be removed together with all of them in one go: a confirmation says how many threads will be deleted, and it's refused while any of them is running. Files on disk are never touched. Renaming changes only the name t3 mini shows (in the sidebar, header, and New thread dialog), never the folder; clear the name to go back to the folder name.

Use the sun/moon/monitor button at the bottom of the sidebar to cycle between Light, Dark, and System themes, or pick one under **Settings → Appearance**. System follows your OS setting.

When a thread finishes, a soft sound plays (pick Soft chime, Marimba, or Pop, or turn it off, under **Settings → Notifications**). A thread that finishes or fails while you aren't looking at it gets a dot and a bold title in the sidebar until you open it. When a thread finishes, fails, stops, or needs approval, a toast appears in the corner. Click it to open that thread. On your first visit, t3 mini offers to turn on desktop notifications, which fire while the window is in the background. They name the project, the agent, and what happened (e.g. “t3-mini · Claude finished”), with the thread's title underneath. With t3 mini open in several tabs, only the tab you used last sends the desktop notification and plays the sound, and only when you aren't on any t3 mini tab; each tab still shows its own toasts. Enable or disable desktop and in-app notifications at any time from **Settings** (gear icon at the bottom of the sidebar). If you blocked notifications in the browser prompt, allow them in your browser's site settings for localhost, then reload.

t3 mini remembers your last agent, project folder, and per-agent model, effort, and permission choices, plus notification, sound, unread, and theme settings, in this browser (`localStorage`), so new threads start with them.

Install and sign in to the providers you want to use:

```sh
# Codex
npm install -g @openai/codex
codex login

# Claude Code (macOS / Linux)
curl -fsSL https://claude.ai/install.sh | bash
claude
```

Claude runs through the Claude Agent SDK using your installed `claude` CLI (`CLAUDE_BIN`, else `claude` on PATH or in `~/.local/bin`), so updating Claude Code updates t3 mini too; without a CLI, the SDK's bundled runtime is used. Both agents use your local provider credentials. The **Settings → Agents** section (a warning icon appears in the sidebar footer when a CLI is missing) reports whether a standalone `claude` / `codex` command is available, its version, and the account each agent is signed in with (e.g. “Signed in · Claude Team”, “· ChatGPT Pro 5x”; the email stays hidden until you click the eye button next to it), as the agents themselves report it (Claude's SDK account info, Codex's `account/read`; no AI call, no token read, cached for five minutes). It does not check account limits. Restart the server after installing a CLI or changing environment settings.

### Agent updates

On the Mac, t3 mini checks npm for new Claude Code and Codex releases (at startup and every six hours). When one is out, a card at the bottom of the sidebar shows the version change with an **Update** button, which runs `claude update` or `codex update` in the background. The next turn uses the new version, and existing threads resume as before. Updating waits until no thread on that agent is running. Hiding the card skips that version in this browser. Phones never see it.

## What it does

- Saved threads, independent provider sessions, and project folders. Each thread has a `/threads/<thread-id>` URL, so refresh, direct links, and browser Back/Forward preserve selection.
- Provider-supplied model pickers, model-specific effort levels, and saved permission modes.
- Agents can show images in the chat (Claude, and Codex threads created from now on): ask “take a screenshot and show me” or “show me the chart you made”. They use t3 mini's `show_image` tool, which only accepts real image files inside the project or temp folder. See [docs/tools.md](docs/tools.md).
- Agents can use a browser to check their work (Claude, and Codex threads created from now on): ask “start the dev server and check the login page”, “click through sign-up and tell me what breaks”, or “screenshot the page on a phone size in dark mode”. The agent opens the page in its own invisible browser (your installed Google Chrome, Microsoft Edge, Brave, or Chromium; nothing is downloaded), reads it, clicks and types, checks the console for errors and failed requests, and takes screenshots, sharing them in the chat when useful. For safety it can only open **local sites** (localhost, 127.0.0.1, *.localhost), never t3 mini itself, and it can't run scripts in the page, upload files, or download. Each thread gets a private session with no cookies or logins from your own browser. Opening a page, clicking, and typing follow the thread's permission setting (no prompts with Full access). See [docs/browser.md](docs/browser.md).
- Agents can draw diagrams in the chat, like Claude Desktop: ask “draw the login flow”, “show the database schema as a diagram”, or “sketch the architecture”. They write Mermaid (flowcharts, sequence, state, class and ER diagrams, Gantt charts, mind maps, timelines, pie charts and more) through t3 mini's `show_diagram` tool, and the chat draws it in a card that matches the light or dark theme. The card has **Diagram / Code** views, a copy button for the Mermaid source, and **Expand** (or click the diagram) for a full-screen view with zoom and **Download SVG**. Wide diagrams scroll sideways rather than shrink to unreadable text. A reply that contains a ` ```mermaid ` code block is drawn the same way (it stays a code block while it streams in, or if it isn't valid Mermaid). Codex threads created before this feature don't have the tool, but their ` ```mermaid ` blocks still draw.
- Agents can rename their own thread: ask “rename this thread to Login bug” or “give this session a better name”. They can't rename other threads. (Codex threads created before this feature don't have it.)
- Agents can run long-lived processes such as dev servers (“start the dev server”): a **● N running** indicator under the composer lists them with their URL, live **Logs**, **Restart**, and **Stop**. They stop when t3 mini stops. Starting one asks for approval unless the thread has full access.
- Streamed Markdown replies (code blocks have a copy button; hovering your messages and the agent's final answers shows the time and a copy button that copies it as written, Markdown included, like Claude Desktop).
- Turns read like Claude Desktop. While the agent works you see its short in-between notes and its steps in the order they happened, close together, with a live, shimmering line at the bottom saying what it's doing now and for how long (e.g. "List the project folder 12s"). When the turn finishes, that work folds into one line, **Worked for 2m 10s · 12 steps ›**, above the final answer (**Stopped after…** / **Failed after…** when it ended early); click it to see everything again. When the agent keeps a to-do list (Claude's to-do tools, which t3 mini turns on for its Claude sessions, or Codex's plan), it shows as a **checklist card** that updates in place: done items are checked, the current one spins, the rest wait; between steps the live line names the current item ("Running the tests"). The card folds away with the rest of the work when the turn ends. Images and diagrams the agent showed you along the way (e.g. screenshots from `show_image`, diagrams from `show_diagram`) don't fold away: they move into the final answer, above its text, in the order they were shown, so the results stay in view and an answer that says "the diagrams above" reads right. Each step is one line: Claude's own description of a command when it gives one ("Build the package and run the tests"), otherwise like `Run git status`, `Read src/app.ts`, or `Edit src/styles.css`, with **Failed** when it failed; click a step to see the full command or edit and its output (long output is trimmed). Steps are kept for the latest run only, so older turns fold just the agent's notes ("· 3 messages"), and steps saved before this layout show after that turn's notes.
- Real provider status: starting, working, waiting for approval, completed, stopped, or failed.
- Explicit **Allow once / Decline** actions when a provider requests tool approval, plus **Stop** for an active turn.
- When Claude asks you a multiple-choice question (its AskUserQuestion tool), a question card shows the options to pick from (or several, when it allows that), plus **Something else** to type your own answer; **Send answer** gives Claude your choice, **Skip** lets it carry on without. Questions appear in every permission mode, including Full access, since they need your answer rather than your permission.
- Work Claude leaves running in the background (a background subagent or shell) keeps the turn open after its last reply; a **Still running in the background** line names it until it finishes, and a subagent's steps are tagged with its task name.
- Live updates over Server-Sent Events, including reconnect snapshots. Switching threads or closing the browser does not stop an agent.
- Recoverable conversations after a server restart. A turn that was active at restart appears as stopped; send a new message to resume its provider session.

Completion comes from the provider's turn result, not from text matching or an inactivity timer. A completed turn means the provider finished responding, not that the requested work was independently validated.

Model catalogs come directly from the local providers and are cached for five minutes. Effort choices follow the selected model’s capabilities (the provider's default model when Provider default is selected). Switching models resets effort to Default. Catalog availability does not guarantee account access. If loading fails, Provider default remains available and the picker offers Retry.

## How it works

```text
Browser → TanStack Start server routes → AgentService
                                       ├─ Codex app-server (JSON-RPC over stdio)
                                       └─ Claude Agent SDK (query + streamed events)
Browser ← Server-Sent Events ← saved thread state
```

Permissions map to each provider’s native modes:

| Mode              | Behavior                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| Approval required | Codex starts read-only and requests approvals for untrusted actions; Claude uses its default permission checks.  |
| Auto-accept edits | Codex allows workspace writes; Claude automatically accepts project edits. Other actions may ask for approval.   |
| Auto              | The provider reviews actions automatically. Availability depends on your provider, model, and account policy.    |
| Full access       | Codex removes its sandbox; Claude bypasses normal permission prompts. This permits actions outside your project. |

New threads default to **Claude** (Codex if only Codex is installed) and **Full access**; once you pick something else, your last choice is used instead. Full access lets the agent run any command and edit files outside your project without asking — use it only with projects and machines you trust, and switch to Approval required for anything sensitive. Threads saved before permission modes existed keep their original mode (Codex: Auto-accept edits; Claude: Approval required). Claude reads your user/project/local settings. Existing provider settings can already allow some tools; approvals appear when the provider asks for them. Neither integration installs a plugin. Provider login stays outside this app.

The **Browse…** chooser opens on the Mac running the server. Cancel leaves the current folder unchanged. On other operating systems, enter the project folder path manually.

This first version runs on one local Node process. It binds to loopback and rejects foreign hosts and cross-origin API requests. Phone access (below) is the only way in from another device. There are no tunnels, worktree isolation, or checkpoint rollback. Use a project folder or worktree you intend the agent to edit. Decline unsupported requests or stop the turn and answer with a follow-up message.

## Dictation

The 🎤 button in the composer records your voice and types the transcript at the cursor: click to record, click again to stop (recordings stop on their own after 5 minutes). Transcription is live: while you speak, the words so far appear in the empty composer's placeholder (the composer grows to fit them; once it's full, the newest words stay in view), and when you stop, the final text is inserted at the cursor. A short sound plays when recording starts and stops; turn it off under **Settings → Dictation → Recording sounds**.

To spell names and code terms right, dictation also uses the thread's vocabulary: the server picks up to 40 unusual words from the agent's last two replies (names like _Deepgram_, identifiers like `useState`, acronyms, and words outside a standard English word list) and sends them to Deepgram as [keyterms](https://developers.deepgram.com/docs/keyterm) with your audio. It never takes them from your messages, code blocks, links, or email addresses, and drops anything that could be a key or token (long or random-looking strings, digits, hex, key prefixes such as `sk-` or `ghp_`). The browser only says which thread you're in; the words are chosen on the server. Turn it off under **Settings → Dictation → Use words from the thread**. Keyterms need a Nova-3 or Flux model, so they're skipped if `DEEPGRAM_MODEL` is set to another one. Transcription uses [Deepgram](https://deepgram.com) (`nova-3` with smart formatting); new Deepgram accounts get free credit, then it's pay-as-you-go.

1. Create an API key at [console.deepgram.com](https://console.deepgram.com).
2. In t3 mini, open **Settings → Dictation**, paste the key, and click **Save**. The server checks it with Deepgram first.
3. Optionally pick a **Microphone** in the same tab (after allowing microphone access once, so the browser shows device names). The choice is remembered per browser and falls back to the system default if that microphone is unplugged.

The key is stored on the Mac in `.data/secrets.json` (owner-only, gitignored) and is never sent back to the browser; Settings shows only its last four characters. Alternatively set `DEEPGRAM_API_KEY` in the environment or in a `.env` file (see `.env.example`), which takes priority. The key can only be viewed or changed on the Mac, not from a paired phone. Audio streams from the browser to the t3 mini server over a local WebSocket (`/api/dictation/stream`, same-origin only) and from there to Deepgram's live API, with Deepgram's model-improvement program opted out (`mip_opt_out=true`). Only the transcript text comes back to the browser. If streaming can't connect, the finished recording is sent to `/api/transcribe` instead, so dictation still works, just without the live preview.

Browsers only allow the microphone on secure pages, so the button appears on the Mac (`localhost`) but not over plain-HTTP phone access; use your phone keyboard's dictation there.

## Phone access

Use t3 mini from your phone's browser, either on the same Wi-Fi (**Local network**) or from anywhere over **Tailscale (HTTPS)**. It's off by default and **turns off whenever the server restarts**.

1. On the Mac, open **Settings → Phone access**, pick a **Connection**, and turn on **Allow phones**. A phone icon appears in the sidebar footer while it's on.
2. Click **Connect a phone** and scan the QR code with the phone's camera. The code works once and expires after 5 minutes.
3. The phone stays paired for 30 days. Revoke one device or all of them in the same section; revoking cuts open connections immediately.

Phones see the same threads live, and can send, steer, approve, stop, and view changes. Mac-only actions (Browse for a folder, Open in VS Code, managing phone access) are hidden on the phone and refused by the server.

**Local network** (plain HTTP): a gateway listens on port `4311` (set `T3_MINI_PHONE_PORT` to change it) only while phone access is on. It accepts requests only for this Mac's own local-network address, only from private network addresses, only with a paired session cookie (`HttpOnly`, `SameSite=Lax`), and only from its own origin, then forwards them to the loopback-only app marked as remote. Traffic isn't encrypted, so use it only on a network you trust (such as home Wi-Fi), never on public or shared Wi-Fi: anyone who can watch the traffic could take over a paired session, and with it agents that can run commands on this Mac. macOS may ask once whether to allow incoming connections for `node`.

**Tailscale (HTTPS)**: encrypted, and works from anywhere (cellular included) without opening ports. Install [Tailscale](https://tailscale.com) on the Mac and the phone, sign both in to the same tailnet, and turn on MagicDNS and HTTPS certificates in the Tailscale admin console (if HTTPS isn't on yet, Settings shows the link to enable it). t3 mini then runs `tailscale serve` to publish the gateway at `https://<this Mac>.<tailnet>.ts.net:8443` (set `T3_MINI_TAILSCALE_PORT` to change the port) to **your tailnet only**; it never uses Tailscale Funnel, so nothing is on the public internet. In this mode the gateway listens on loopback only, so nothing is exposed on your Wi-Fi either, and the serve entry is removed when phone access turns off or t3 mini stops. Phones still pair with a QR code: being on the tailnet isn't enough on its own. Over HTTPS the phone can also use the microphone for **dictation** and the clipboard. Set `TAILSCALE_BIN` if the `tailscale` command isn't on your PATH or in `/Applications/Tailscale.app`.

Session tokens and pairing codes are stored only as SHA-256 hashes in `.data/devices.json`. Phones get in-app toasts and sound for finished threads; system notifications on phones would need a home-screen web app with push, which t3 mini doesn't do yet.

Developer details (architecture, security invariants, pitfalls, tests): [docs/phone-access.md](docs/phone-access.md).

## Data and configuration

Conversations are atomically saved to `.data/threads.json`, projects to `.data/projects.json`, and attachments under `.data/attachments/` (all gitignored). Deleting a thread does not delete its attachments. Creating a thread also saves its folder as a project. Provider session IDs are kept so later messages continue the same conversation. Deleting a thread removes its t3 mini history; the provider may retain its own native session history. Back up `.data` if you need it.

| Environment variable     | Purpose                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `T3_MINI_DATA_DIR`       | Override the `.data` directory.                                                                                                                |
| `CODEX_BIN`              | Codex executable path; defaults to `codex` on PATH.                                                                                            |
| `T3_MINI_BROWSER`        | Path to the Chromium-based browser the agents' browser tools use; defaults to Google Chrome, then Microsoft Edge, Brave, or Chromium.          |
| `CLAUDE_BIN`             | Claude Code executable for the SDK, CLI check, and updates; defaults to `claude` on PATH or in `~/.local/bin`, else the SDK's bundled runtime. |
| `PORT`                   | Production server port; defaults to `4310`.                                                                                                    |
| `VSCODE_BIN`             | Optional `code` executable used by the Open in VS Code button.                                                                                 |
| `T3_MINI_PHONE_PORT`     | Port for phone access on your local network; defaults to `4311`.                                                                               |
| `T3_MINI_TAILSCALE_PORT` | HTTPS port for phone access over Tailscale; defaults to `8443`.                                                                                |
| `TAILSCALE_BIN`          | Tailscale CLI path; defaults to `tailscale` on PATH, then the one inside `/Applications/Tailscale.app`.                                        |
| `DEEPGRAM_API_KEY`       | Deepgram key for dictation; overrides the one saved in Settings.                                                                               |
| `DEEPGRAM_MODEL`         | Deepgram model for dictation; defaults to `nova-3`.                                                                                            |

`bun run dev` and `bun run start` load a `.env` file if present. Use one server process per data directory. Runtime credentials and environment variables are never sent to the browser. Conversations and tool inputs may contain project information, so keep the data directory private.

## Production and checks

```sh
bun run build
bun run start

bun run typecheck
bun run test
```

The production Node server serves the built client, SSR, API routes, and event streams on localhost. This app needs a long-running local Node process with filesystem and CLI access; static-only and edge hosting cannot run these adapters.

Tests cover lifecycle transitions, approvals, stopping, concurrent submissions, disk recovery, request origin checks, and the Codex stdio protocol using a local fixture. No paid provider calls are made by the test suite.

References: [TanStack Start](https://tanstack.com/start/latest/docs/framework/react/build-from-scratch), [Codex app-server](https://learn.chatgpt.com/docs/app-server), [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk).
