# Agent guide for t3 mini

A small local web app for running Codex and Claude Code threads on project folders (a mini t3code). The README covers usage; this file is for agents changing the code.

## Commands

```sh
bun run dev        # Vite dev server on http://127.0.0.1:4310
bun run test       # vitest (no paid provider calls; providers use fixtures/mocks)
bun run typecheck  # tsc --noEmit
bun run build
bunx prettier --write .
```

Run typecheck, tests, and build before committing. Keep the README (and `docs/`) in sync with behavior changes.

## Things to know

- **Restart the dev server after server changes.** The service and the phone-access gateway live on `globalThis` so running agents survive hot reloads; new server code only takes effect after restarting `bun run dev`. Check that no thread is running first (`/api/bootstrap`, status `starting`/`working`/`waiting`), since a restart interrupts running turns.
- **Keep the thread view fast.** Typing must not re-render the page: the composer textarea is uncontrolled (`draftText` ref + `hasDraft` flag in `Workspace.tsx`), so don't turn it back into `value={…}` state. Messages render through memoized `MessageView` / `MessageMarkdown` (Markdown parsing is the expensive part, ~100 ms for 80 replies; parsed replies are also cached across thread switches by `parseMarkdown()`), and `DiffPanel` is memoized with stable props (`closeDiff`). Keep new props to these stable, or they'll re-render on every live update. Long threads draw only their latest turns (`firstTurns`, `OlderTurns` adds more near the top, anchored to a turn key so new turns don't shift you) and remember each thread's place per tab (`places`, `savePlace`, `restorePlace`); keep scroll changes going through `pin()` and the settle window. Live updates (`/api/events`) send only the snapshot parts that changed for that tab (`changedParts()` in `api.ts`); a missing key means unchanged, so the client must only set state for keys that are present.
- **Don't use `instanceof` on server error classes across modules.** After a hot reload the long-lived service throws errors from an older copy of `service.ts`, so `instanceof HttpError` fails and real 404s/409s turn into 500s. `api.ts` uses `isHttpError()` (checks by name and `status`); follow that pattern for new error types.
- **Check Base UI first, before building any UI piece yourself.** Before writing a custom component or interaction (menus, popovers, dialogs, tooltips, tabs, switches, selects, avatars, toasts, sliders, progress, scroll areas, and the like), look for it in Base UI: the parts installed in `node_modules/@base-ui/react/` (one folder per component) and the docs at https://base-ui.com/react/components. Use it when it exists; build custom only when Base UI has nothing that fits, and say why in a comment.
- **UI primitives come from [Base UI](https://base-ui.com) (`@base-ui/react`, pinned).** Menus, submenus, and the context menu use `Menu`; dialogs go through `Modal` (`Dialog`); confirmations go through `useConfirm()` (`ConfirmDialog.tsx`, Base UI `AlertDialog`), never the browser's `confirm()`; the process list is a `Popover`; tabs, switches (`Toggle`), segmented controls (`Segmented`), and the microphone picker are `Tabs`, `Switch`, `RadioGroup`, and `Select`; project avatars are `Avatar` (image with a letter fallback). Use these for new UI instead of hand-rolled focus, keyboard, or positioning code. Base UI is unstyled: style its parts with classes in `styles.css` and its state attributes (`data-highlighted`, `data-checked`, `data-popup-open`, `data-disabled`). Popups are portaled to `<body>` and share one layer (`z-index: 50`), so whichever opened last is on top; `.workspace` has `isolation: isolate` so they always cover the app.
- **Security posture.** The app listens on loopback only and rejects foreign hosts and cross-origin requests (`checkRequest`). Agents can run arbitrary commands, so any new way in must authenticate. Phone access is the only remote entry point (local network over HTTP, or Tailscale over HTTPS via `tailscale serve`, never Funnel); read `docs/phone-access.md` before touching it.
- **Phones run in an insecure context** (plain HTTP on a LAN address). Don't use `crypto.randomUUID`, `navigator.clipboard`, or other secure-context-only APIs in client code; see `docs/phone-access.md` → Pitfalls.
- **Secrets stay on the server.** The Deepgram key comes from `DEEPGRAM_API_KEY` or `.data/secrets.json` (mode 0600); APIs return only `configured`/`source`/last-4 `hint`, and key management is Mac-only. Never log keys or send them to the browser. Live dictation relays audio through the server (`dictation-stream.ts`) for this reason; its WebSocket is wired into Vite (`vite.config.ts`) and `server.mjs` via an upgrade hook and enforces the same loopback/same-origin rules, accepting paired phones only through the authenticated gateway.
- **Commands run without a shell** (`execFile` with argument arrays, `--` before paths). Keep it that way.
- **Where state lives.** Per-device state (notification prefs, sidebar width/hidden, diff panel, drafts, unread markers, dictation mic) lives in `localStorage`; wrap access in try/catch. Shared state lives on the server: threads, projects, devices, and view settings that should match in every window (`UiSettings` in `.data/ui.json`: Group by, theme, project icons, animations, agent defaults, collapsed projects, background music). Shared view settings go through `src/shared-settings.ts` (`registerShared` / `shareSetting`, validated by `server/ui-settings.ts`), keep a local copy for instant load, and are only re-applied when their value changes.
